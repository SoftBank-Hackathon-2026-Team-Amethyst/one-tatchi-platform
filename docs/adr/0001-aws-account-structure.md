# 0001. AWS 계정 구조와 팀 접근 방식

- 상태: 채택
- 날짜: 2026-10-08
- 관련: T23 (#23), 설계 문서 6.6, 코드 [`org/`](../../org)

## 배경

팀원 5명이 AWS를 써야 한다. 계정은 팀원 개인 계정 하나뿐이고 크레딧은 30만원(약 $210)이다. 개인 리소스와 프로젝트 리소스를 섞지 않고, 끝나면 깔끔하게 정리할 수 있어야 한다.

## 결정

1. **개인 계정을 관리 계정으로 두고, 프로젝트 전용 멤버 계정 `one-tatchi`를 만든다(AWS Organizations).**
2. **팀원 접근은 IAM Identity Center로만 한다.** IAM 사용자 · 액세스 키는 만들지 않는다. CLI는 `aws configure sso`.
3. **권한 세트는 2개로 가볍게 둔다.** 인프라를 만지는 4명은 `AdministratorAccess`, 1명은 `ReadOnlyAccess`. 관리 계정 접근은 조직 관리자 1명만.
4. **넓은 권한 대신 SCP로 바깥을 막는다.** 서울 리전만, 조직 탈퇴 · 계정 해지 금지, EC2 · RDS 인스턴스 타입 제한. 멤버 계정 루트 자격증명은 두지 않는다(중앙관리).
5. **예산 경보는 크레딧을 뺀 금액으로 본다.** 월 $200, 50/80/100% 실제 + 100% 예측.
6. **조직 · 계정 · 권한은 Terraform(`org/`)으로 관리하고, apply는 관리자가 로컬에서만 한다.** 관리 계정에 CI(OIDC)를 열지 않는다.
7. **Identity Center MFA는 끈다.** 첫 로그인은 이메일 OTP로 비밀번호를 정한다.
8. **GCP는 T4 시작 때 세팅한다.**

## 대안

| 대안 | 버린 이유 |
|---|---|
| 개인 계정 안에서 IAM 사용자 · 정책으로 격리 | EKS · OIDC 작업에 IAM 생성 권한이 필요하고, 그 권한이면 계정 전체를 가질 수 있다. 개인 리소스와 청구가 섞이고 계정째 정리할 수 없다 |
| 새 독립 계정 | 크레딧 · 결제를 따로 관리해야 한다. Organizations면 관리 계정에 등록한 크레딧이 공유된다 |
| 세밀한 권한 세트(PowerUser + 제한된 IAM 등) | EKS · IRSA · OIDC 역할 생성에 막혀 해커톤 속도를 못 낸다. 멤버 계정과 SCP가 경계 역할을 하므로 계정 안에서는 넓게 준다 |
| 관리 계정 작업을 GHA로 apply | public 레포 CI가 조직 전체 권한을 갖게 된다 |

## 결과

- 팀원은 각자 계정으로 로그인하고 장기 키가 없다(6.6 "장기 키 없음").
- 프로젝트가 끝나면 `one-tatchi` 계정만 닫으면 된다.
- **MFA를 끈 대가:** `AdministratorAccess`(관리 계정 포함)가 비밀번호 하나에 의존한다. 포털 URL과 username이 레포에 공개되어 있어 맞춤 피싱의 재료가 된다. 해커톤 기간의 편의를 택했고, 사고가 나도 피해 범위는 SCP로 서울 리전 · 허용 인스턴스 타입 안으로 묶인다. 기간이 길어지거나 실사용자가 생기면 다시 켠다(context-aware 권장).
- 서비스 연결 역할(EKS 노드 그룹의 Auto Scaling 등)에는 SCP가 적용되지 않아, 인스턴스 타입 제한은 사람이 직접 띄우는 경우만 막는다. 노드 타입은 Terraform 리뷰로 관리한다.
- 크레딧 대비 EKS 비용이 크다(컨트롤 플레인만 클러스터당 월 약 $73). 클러스터 수와 NAT 개수는 T5 · T24에서 예산을 보고 정한다.
