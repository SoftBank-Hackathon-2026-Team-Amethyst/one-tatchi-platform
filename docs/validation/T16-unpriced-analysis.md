# T16 미조회 비용 항목 원인 분석

분석일: 2026-10-09. 대상: C7 demo-app 임시 사본의 실제 가격 조회 결과.

후속 작업에서 아래 미조회 25개의 연결을 모두 보완했다. 추가 과금 차원을 포함해 AWS 21개·GCP 23개 가격표를 실조회했고, 조회 실패는 0개였다. 이 문서는 수정 전 원인 분석이며 현재 결과는 [매핑 구현·검증 기록](T16-catalog-mapping.md)을 따른다. 월 사용량과 무료 적용 조건이 없는 항목은 계속 비용 미산정이다.

## 결론

미조회 25개는 이번 실행에서 공급자 가격 API의 오류로 실패한 항목이 아니다. 17개는 정확한 과금 항목을 선택하는 입력이 부족하고, 8개는 조회 코드에 자원 종류와 과금 차원의 연결이 없다. 모두 API 요청 전 검사에서 중단된다. 따라서 재로그인이나 재시도만으로 해결되지 않는다.

AWS의 11개, GCP의 노드 CPU·메모리 2개는 실제 조회에 성공했다. 이 사실은 다른 항목의 조회 지원이나 전체 견적 완성을 보장하지 않는다. 앞서 발생한 GCP v1 카탈로그 페이지 조회 지연은 별도 문제이며, 이번 미조회 25개의 직접 원인과 구분한다.

## 항목별 직접 원인

| 대상 | 항목 | 개수 | 이번 실행의 중단 원인 | 필요한 보완 |
|---|---|---:|---|---|
| AWS | 로그 수집·저장 | 2 | `attributes`가 비어 있고 필수 `usage_type`이 없음 | 실제 로그 서비스·종류를 확인해 정확한 과금 항목을 지정 |
| AWS | 인터넷 송신 | 1 | `usage_type`, `to_location`이 없음 | 송신 출발지·목적지·서비스에 맞는 과금 항목을 지정 |
| AWS | 공인 IPv4, 메트릭, 시크릿, 감사 저장소 | 4 | `PROFILES`에 해당 자원 종류·과금 차원 조합이 없음 | 서비스별 조회 연결과 과금 차원을 구현하고 자원 목록도 보완 |
| GCP | GKE 클러스터, 노드 디스크 | 2 | 필수 카탈로그 선택 정보가 없음 | 정확한 SKU와 서비스·리전·과금 단위를 지정 |
| GCP | Cloud NAT 시간·처리량 | 2 | 동일 | NAT의 실제 과금 수량·단위까지 확인 |
| GCP | test/prod 로드밸런서 시간·처리량 | 4 | 동일 | 노출 방식과 과금 SKU·수량을 확인 |
| GCP | Cloud SQL 인스턴스·저장소 | 2 | 동일 | 공유 코어 인스턴스 규격과 저장소 SKU를 확인 |
| GCP | Artifact Registry 저장소 | 1 | 동일 | 서비스와 저장량 과금 SKU를 지정 |
| GCP | 로그 수집·저장, 인터넷 송신 | 3 | 동일 | 로그 유형·저장 조건, 송신 목적지별 SKU를 확인 |
| GCP | 공인 IPv4, 메트릭, 시크릿, 감사 저장소 | 4 | `PROFILES`에 해당 자원 종류·과금 차원 조합이 없음 | 서비스별 조회 연결과 과금 차원을 구현하고 자원 목록도 보완 |

GCP의 14개는 `resource_family`, `resource_group`, 그리고 정확한 `description` 또는 `sku_id`를 요구하는 검사에서 실패한다. 필드를 채운 뒤에도 SKU의 리전·종량제 조건·단위와 무료 구간 처리 검증을 통과해야 한다. 입력 보완만으로 모두 해결된다고 확정할 수는 없다.

`unsupported_resource`라는 오류 코드는 현재 두 원인을 함께 표현한다. 지원되는 종류지만 입력이 부족한 경우와 조회 기능 자체가 없는 경우를 같은 코드로 표시하므로, 코드 이름만 보고 공급자 API에서 지원하지 않는 항목이라고 해석하면 안 된다.

## 자원 목록에서 추가로 확인한 문제

1. 추가 항목의 `attributes`가 비어 있고 일부 출처가 실제 구성 대신 매핑 문서를 가리킨다. 비용 누락 방지를 위한 항목 선언과 정확한 과금 대상으로 확인된 항목을 구분해야 한다.
2. 메트릭의 `request`, 시크릿의 `gb_month`는 현재 목록의 임시 표현이다. 서비스별 실제 과금 차원을 검증하지 않았으므로 필터만 추가해 이 단위로 계산하면 안 된다.
3. AWS는 RDS의 `manage_master_user_password=true`로 Secrets Manager를 사용하고, demo-app은 Slack 봇의 기존 Secrets Manager 시크릿도 참조한다. GCP DB 모듈은 Secret Manager 시크릿·버전을 생성한다. 시크릿 비용을 미사용으로 일괄 제외할 근거가 없다.
4. AWS는 중앙 Prometheus와 5Gi 영구 디스크를 사용하면서 별도의 CloudWatch 증거 로그 그룹도 선언한다. 자체 Prometheus 저장 비용과 CloudWatch 비용을 구분해야 한다. Grafana에서 CloudWatch를 조회한다는 사실만으로 모든 메트릭에 유료 수집 비용을 추가할 수는 없다.
5. GCP는 시스템·워크로드 로그와 Managed Prometheus를 활성화한다. 기능 활성화는 확인됐지만 월 사용량과 적용되는 과금·무료 조건은 별도 확인 대상이다.
6. AWS bootstrap에는 S3 감사 로그 버킷이 있다. 공유 bootstrap 비용의 포함 범위와 저장량을 정해야 한다. GCP의 일반적인 감사 저장소 항목은 별도 저장소·로그 유형·보존 설정을 먼저 확인해야 하며, AWS 항목을 그대로 대응시켜서는 안 된다.

## 단가 조회와 월 비용 확정은 별개다

단가를 조회해도 트래픽 GB, 로그 수집·저장량, 이미지 저장량, 메트릭 사용량 등을 모르면 월 비용은 확정할 수 없다. 이번 결과의 미조회 25개 외에도 월 사용량·앱 추가분·수용량이 미정인 항목이 남아 있다. 단가 미조회 개수와 월 비용 미산정 개수는 같지 않다.

구성에 존재하는 비용은 조회·계산을 보완한다. 실제 사용하지 않는 서비스만 고정된 구성 근거와 함께 제외한다. 범위 밖 비용을 제외하려면 보고서에 견적 범위를 명시한다. 미조회나 사용량 미정을 0원으로 바꾸지 않는다.

## 보완 순서

1. GCP 기본 인프라 11개 항목의 정확한 카탈로그 선택과 과금 수량을 연결한다. 노드 CPU·메모리만으로 GCP 전체 비용을 표현하지 않는다.
2. AWS/GCP의 로그·송신 항목을 실제 서비스와 목적지에 맞춰 연결한다.
3. IPv4·시크릿 등 실제 사용되는 추가 자원의 서비스별 과금 차원과 조회 기능을 추가한다. 메트릭·감사 저장소는 구성과 견적 범위를 먼저 확정한다.
4. 변동 사용량은 근거 있는 범위로 입력하거나 미정으로 남긴다. 조회와 계산 결과를 각각 검증한다.

## 근거와 검증 범위

- 입력·결과: `/tmp/t16-c7-app/.deploy/analysis/pricing-input.json`, `prices.json`, `pricing-inventory.json`.
- demo-app 구성 기준: 커밋 `7893547913b57705d7f2e366f375b15beadcbba4`, 모듈 태그 `v1.16.0`.
- 조회 검사: `skills/deploy-analyze/scripts/pricing_aws.py`의 `PROFILES`·`filters`, `pricing_gcp.py`의 `PROFILES`·`_lookup`.
- 구성 근거: demo-app AWS/GCP 루트, platform `modules/database`, `modules/cluster/gcp`, `modules/observability`, `bootstrap/main.tf`. 확인한 플랫폼 모듈은 `v1.16.0`과 차이가 없다.
- 재현: 공급자 메타데이터 접근 함수를 호출하면 즉시 실패하도록 대체하고, 저장된 입력의 미조회 25개를 검사했다. 25개 모두 네트워크 접근 이전에 동일한 입력 부족·미지원 오류를 재현했다.
- 이 분석에서는 새로운 가격 API 조회, 배포, 인프라 변경을 수행하지 않았다. 입력을 보완한 이후의 공급자 응답은 아직 검증하지 않았다.
