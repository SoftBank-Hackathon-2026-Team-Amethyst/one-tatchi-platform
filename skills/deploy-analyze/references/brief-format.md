# 배포 브리프 계약

T15 / GitHub #2의 질문·입력·저장 규칙. 스킬 원본은 platform에, 결과는 대상 앱의 `.deploy/`에 둔다. 이 계약은 후속 분석과 T6 운영 관문이 함께 사용한다.

## 선택형 질문 흐름

질문 문구와 선택지, 저장값의 원본은 [brief-questions.json](brief-questions.json)이다. `write_brief.py --questions`가 원문을 그대로 담은 `AskUserQuestion` 입력을 `batches` 배열로 출력한다. 각 객체를 그대로 전달하고 `multiSelect: false`를 유지한다. 선택지를 임의로 생성하거나 `100명 이하`를 `100명`으로 줄이지 않는다.

Claude Code는 한 호출에 최대 4문항, 문항당 2~4개 선택지를 지원한다. 따라서 첫 메뉴는 1~4번, 다음 메뉴는 5번으로 구성한다. 사용자가 항목을 하나씩 선택하며 이동하도록 하고, 첫 메뉴 제출 뒤 요약이나 계속 여부 질문 없이 바로 다음 메뉴를 연다. 한 화면에 다섯 문항을 넣는 것은 현재 도구에서 지원하지 않는다. [공식 도구 제한](https://code.claude.com/docs/en/agent-sdk/user-input#limitations)

이미 명확히 답한 항목은 제외할 수 있다. 도구가 없으면 같은 선택지를 한 질문씩 대화로 제시한다. 다섯 항목의 답변 또는 명시적인 건너뛰기가 모두 모인 뒤에만 파일을 저장한다. 무응답·취소·시간 초과를 선택이나 건너뛰기로 처리하지 않는다.

| 순서 | 항목 | 고정 선택지 |
|---|---|---|
| 1 | 하루 예상 사용자 수 | 100명 이하 / 101~1,000명 / 1,001~10,000명 / 10,001명 이상 |
| 2 | 월 인프라 예산 (원화) | 10만 원 이하 / 10만 원 초과~50만 원 이하 / 50만 원 초과~100만 원 이하 / 100만 원 초과 |
| 3 | 개인정보, 결제, 금융 데이터 등 민감한 데이터를 저장하거나 처리하나요? | 예 / 아니오 / 모름 |
| 4 | 배포 대상 | AWS / GCP / 온프레미스 / 추천 |
| 5 | 가용성 | 시연용 / 일반 운영 / 중단에 민감 / 모름 |

선택형 메뉴에 별도의 직접 입력 선택지를 추가하지 않는다. Claude Code가 기본 제공하는 `Other` 입력 칸은 스킬에서 숨길 수 없다. 배포 대상은 그 칸을 통해 들어와도 네 선택지 중 하나만 인정한다. Azure나 임의 서버명처럼 다른 값이면 네 선택지를 다시 제시하며 `auto`로 임의 변환하지 않는다. [기본 질문 UI](https://code.claude.com/docs/en/tools-reference#askuserquestion-tool-behavior)

사용자 수와 예산을 직접 숫자로 답하면 해당 범위를 안내하고 선택을 확인한다. 예산은 KRW만 받으며 통화를 묻거나 USD 선택지를 추가하거나 임의 환산하지 않는다. 모름/건너뛰기를 명시하면 각 항목의 `skip_value`를 사용한다. 사용자 수·예산은 `null`, 민감 데이터·가용성은 `unknown`, 배포 대상은 `auto`다. 범위 선택과 미정을 혼동하지 않는다.

민감 데이터의 구체적인 종류나 샘플은 수집하지 않는다. `예`라고 답했다고 개인정보·결제·금융을 모두 다룬다고 기록하지 않는다. 코드에서 로그인·결제 기능을 발견했는데 답변은 `아니오`라면 해당 사실을 알려 그 답변만 확인한다. 모호하거나 상충하는 답변을 임의로 `아니오`로 바꾸지 않는다.

## 저장 스크립트 입력

JSON 객체에 다음 다섯 키를 모두 전달한다. 질문 정의의 `field`를 키로, 선택한 옵션의 `value`를 값으로 사용한다. 스크립트는 같은 정의를 읽어 검증하므로 임의 범위, 외화, 미지원 배포 대상은 거부한다. 키 누락·추가, 중복 키, 잘못된 타입도 오류다.

```json
{
  "expected_daily_users": {"min": 0, "max": 100},
  "monthly_budget": {"min": 0, "max": 100000, "currency": "KRW"},
  "handles_sensitive_data": "yes",
  "preferred_target": "aws",
  "availability": "demo"
}
```

- `expected_daily_users`: 선택지에 정의된 `{min, max}` 또는 `null`. 하루 기준이며 동시 접속자 수가 아니다.
- `monthly_budget`: 선택지에 정의된 `{min, max, currency: "KRW"}` 또는 `null`. 원 단위 정수 범위다.
- 두 범위의 `min`과 `max`는 모두 포함되는 경계다. 마지막 구간의 `max: null`은 상한을 아직 모른다는 뜻이며 예산 무제한을 뜻하지 않는다. 범위 전체를 저장하며 상한만 추출해 사용자의 정확한 답변처럼 기록하지 않는다. 후속 분석이 수치를 가정하면 그 가정을 별도로 밝혀야 한다.
- `handles_sensitive_data`: `yes | no | unknown`. 예·아니오·모름에 대응한다.
- `preferred_target`: `aws | gcp | onprem | auto`만 허용한다.
- `availability`: `demo | standard | high | unknown`.

이전 초안의 단일 사용자 수, `monthly_budget.amount`, `data_categories` 입력은 더 이상 사용하지 않는다. 이전 브리프를 재사용할 때는 새 범위와 예·아니오·모름 선택을 사용자에게 확인한다. 저장 스크립트가 기존 브리프를 읽어 자동 변환하지는 않는다.

저장 시 `--project-root`로 이미 존재하는 앱 루트를 명시한다. `--answers`에 JSON 파일을 주거나 생략/`-`로 표준 입력을 사용한다. `--dry-run`은 검증과 기존 설정 충돌 검사만 하고 파일을 쓰지 않는다. `--questions`는 저장 옵션과 함께 사용할 수 없다. 종료 코드 0은 성공, 2는 입력·설정·파일 오류다. 저장 성공 시 표준 출력은 `compliance`, `needs_review`, `defaults_applied`, 출력 경로를 담은 JSON이다.

## compliance 분류

이 값은 프로젝트의 운영 승인 경로를 선택하는 정책 값이다. 사용자가 제공한 데이터 취급 답변으로 분류하며 AI가 임의로 `none`을 선택하지 않는다.

| 민감 데이터 취급 답변 | 저장할 값 | 브리프 근거 |
|---|---|---|
| 예 (`yes`) | `regulated` | 민감한 데이터를 저장하거나 처리한다고 응답 |
| 아니오 (`no`) | `none` | 민감한 데이터를 저장하거나 처리하지 않는다고 응답 |
| 모름 / 명시적 건너뛰기 (`unknown`) | `regulated` | 확인 전까지 승인 생략을 허용하지 않음; `needs_review: true` |

미정에 대한 보수적 기본값은 T15의 처리 규칙이다. 실제 데이터 취급 여부가 확정되면 사람이 검토해 설정을 변경한다. janto/yolo 모드에 관계없이 이 규칙은 동일하다. 실제 운영 승인 강제와 저장소 경로 보호는 T6에서 구현한다.

## 출력과 기존 파일 처리

- `.deploy/brief.md`: 다섯 답변(범위 포함), 미정/기본값 목록, 규제 분류와 근거, 후속 분석이 재사용할 정규화 JSON을 기록한다. 동일 답변은 동일 문서를 생성한다.
- `.deploy/config.yaml`: `compliance`만 최초 생성한다. `template_version`, 배포 대상, 서비스 크기 등은 여기서 정하지 않는다. 기존 파일에 해당 키가 없다면 다른 값과 주석을 보존해 추가한다.
- 기존 `compliance`가 같으면 `config.yaml`은 바이트 단위로 그대로 두고 브리프만 갱신한다. 기존 값이 다르거나 유효하지 않으면 두 파일 모두 쓰지 않고 실패한다. 기존 브리프도 보존한다. 우회용 강제 덮어쓰기 옵션은 제공하지 않는다.
- YAML은 단일 매핑 문서여야 한다. 중복 키와 잘못된 YAML은 오류다. 출력 경로의 심볼릭 링크는 따라가지 않는다.
- 브리프는 재생성되는 파일이다. 입력·설정 검증을 모두 마친 뒤 각 파일을 임시 파일로 작성하고 교체한다. 여러 파일의 교체를 하나의 트랜잭션으로 보장하지는 않는다.

생성 예시:

```yaml
# .deploy/config.yaml
compliance: regulated
```

## 검증

자동 테스트는 `tests/test_write_brief.py`에 있다. 질문 도구 입력의 개수 제한, 범위 경계와 보존, KRW 고정, 예·아니오·모름 분류, 미지원 대상 거부, 기존 설정 보호, CLI 파일 생성을 확인한다.

Claude Code 대화 검증은 설치본을 갱신한 뒤 클라우드가 필요 없는 임시 앱 디렉터리에서 한다.

1. 새 대화에서 `/deploy-analyze`를 실행한다. 첫 선택지가 `100명 이하`인지, 첫 메뉴에 1~4번이 들어 있는지 확인한다. 선택 후 다음 항목으로 이동하고, 제출 뒤 중간 설명 없이 5번 메뉴가 이어져야 한다.
2. `100명 이하 / 10만 원 이하 / 예 / AWS / 시연용`을 선택한다. 브리프에 두 범위가 유지되고 `compliance: regulated`가 생기는지 확인한다.
3. 별도 빈 디렉터리에서 민감 데이터에 `아니오`를 선택해 `none`, `모름`을 선택해 `regulated`와 미정 근거가 생기는지 각각 확인한다.
4. 사용자 수·예산을 명시적으로 모름/건너뛰기 처리하면 `null`이 저장되는지 확인한다. 메뉴 취소나 미응답 상태에서는 파일을 저장하지 않아야 한다.
5. 배포 대상에 Azure를 입력하면 네 선택지를 다시 제시하는지 확인한다. 원화 예산을 USD로 바꾸거나 범위를 단일 숫자로 저장하지 않아야 한다.
6. 이미 `regulated`인 디렉터리에서 `아니오`를 선택한다. 보호 오류를 안내하고 기존 두 파일을 보존하는지 확인한다.
