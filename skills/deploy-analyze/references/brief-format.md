# 배포 브리프 계약

T15 / GitHub #2의 질문·입력·저장 규칙. 스킬 원본은 platform에, 결과는 대상 앱의 `.deploy/`에 둔다. 이 계약은 후속 분석과 T6 운영 관문이 함께 사용한다.

## 질문 다섯 개

이미 명확히 답한 항목은 다시 묻지 않는다. 숫자는 단위를 함께 받고, 질문 도구의 선택지 외에 직접 입력을 허용한다. 일반 질문과 데이터 취급 질문 모두 명시적인 건너뛰기만 기본값으로 바꾼다.

| 항목 | 질문 문구 | 답변과 선택지 | 모름 / 건너뛰기 |
|---|---|---|---|
| 사용자 수 | 하루에 서비스를 이용할 사용자는 몇 명 정도인가요? 동시 접속자 수가 아닌 하루 기준으로 알려 주세요. | 0 이상의 정수 직접 입력. 범위로 답하면 계획에 사용할 상한을 확인한다. | `expected_daily_users: null`; 미정으로 기록, 규모를 임의로 정하지 않음 |
| 월 예산 | 서버·DB 등 인프라에 쓸 월 예산과 통화는 무엇인가요? 예: 10만 원, 100 USD | 0 이상의 금액과 통화. 단위가 분명한 자연어를 숫자로 정규화한다. | `monthly_budget: null`; 비용 분석에 예산 미정 전달 |
| 데이터 취급 | 개인정보(이메일·전화번호 등), 결제, 금융 데이터를 하나라도 저장하거나 처리하나요? 해당 종류를 알려 주세요. | 개인정보 / 결제 / 금융 중 해당하는 종류 모두, 또는 모두 해당 없음, 또는 모름. 질문 도구가 복수 선택을 지원하지 않으면 자유 입력을 사용한다. | `data_categories: null`; `regulated`를 보수적으로 적용 |
| 배포 대상 | AWS, GCP, 직접 운영하는 서버 중 선호하는 배포 장소가 있나요? | AWS / GCP / 온프레미스 / 추천받기 | `preferred_target: "auto"`; 확정 대상이 아닌 추천 요청 |
| 가용성 | 서비스가 잠깐 멈춰도 되는 시연용인가요, 일반 운영용인가요, 중단에 특히 민감한 서비스인가요? | 시연용 / 일반 운영 / 중단에 민감 / 모름 | `availability: "unknown"`; 특정 SLA를 임의로 약속하지 않음 |

데이터 종류만 수집한다. 실제 이메일·카드번호·계좌번호 등 데이터 샘플은 요청하거나 브리프에 저장하지 않는다. 코드에서 로그인·결제 기능을 발견했는데 답변은 '모두 해당 없음'이라면 해당 사실을 알려 다시 확인한다. `없음`과 다른 종류를 동시에 답하거나 `모름`과 확정 답변을 섞으면 한 가지 의미로 확인한다.

## 저장 스크립트 입력

JSON 객체에 다음 다섯 키를 모두 전달한다. 키 누락은 아직 질문에 답하지 않은 상태로 보고 오류를 낸다. 명시적 건너뛰기는 위 표의 값으로 전달한다. 스크립트는 추가 키, 잘못된 타입·선택지, 중복 키를 거부한다.

```json
{
  "expected_daily_users": 100,
  "monthly_budget": {"amount": 100000, "currency": "KRW"},
  "data_categories": ["personal"],
  "preferred_target": "aws",
  "availability": "demo"
}
```

- `expected_daily_users`: 0 이상의 정수 또는 `null`.
- `monthly_budget`: `null` 또는 `amount`(0 이상의 유한한 숫자), `currency`(대문자 3자리 통화 코드, 예: KRW / USD / JPY)를 가진 객체. 통화 변환은 하지 않는다.
- `data_categories`: `personal`, `payment`, `financial` 중 중복 없는 배열. 명시적 '모두 해당 없음'은 `[]`, 미정은 `null`이다. 단순한 무응답으로 `[]`를 만들지 않는다.
- `preferred_target`: `aws | gcp | onprem | auto`.
- `availability`: `demo | standard | high | unknown`.

대상 루트는 `--project-root`로 명시한다. `--answers`에 JSON 파일을 주거나 `-`로 표준 입력을 사용한다. `--dry-run`은 검증과 기존 설정 충돌 검사만 하고 파일을 쓰지 않는다. 종료 코드 0은 성공, 2는 입력·설정·파일 오류다. 성공 시 표준 출력은 `compliance`, `needs_review`, `defaults_applied`, 출력 경로를 담은 JSON이다.

## compliance 분류

이 값은 프로젝트의 운영 승인 경로를 선택하는 정책 값이다. 사용자가 제공한 데이터 취급 답변으로 분류하며 AI가 임의로 `none`을 선택하지 않는다.

| 데이터 취급 답변 | 저장할 값 | 브리프 근거 |
|---|---|---|
| 개인정보·결제·금융 중 하나 이상 | `regulated` | 사용자가 취급한다고 답한 종류 |
| 모두 해당 없다고 명시 (`[]`) | `none` | 세 종류 모두 취급하지 않는다고 응답 |
| 모름 / 명시적 건너뛰기 (`null`) | `regulated` | 확인 전까지 승인 생략을 허용하지 않음; `needs_review: true` |

미정에 대한 보수적 기본값은 T15의 처리 규칙이다. 실제 데이터 취급 여부가 확정되면 사람이 검토해 설정을 변경한다. janto/yolo 모드에 관계없이 이 규칙은 동일하다. 실제 운영 승인 강제와 저장소 경로 보호는 T6에서 구현한다.

## 출력과 기존 파일 처리

- `.deploy/brief.md`: 다섯 답변, 미정/기본값 목록, 규제 분류와 근거, 후속 분석이 재사용할 정규화 JSON을 기록한다. 동일 답변은 동일 문서를 생성한다.
- `.deploy/config.yaml`: `compliance`만 최초 생성한다. `template_version`, 배포 대상, 서비스 크기 등은 여기서 정하지 않는다. 기존 파일에 해당 키가 없다면 다른 값과 주석을 보존해 추가한다.
- 기존 `compliance`가 같으면 `config.yaml`은 바이트 단위로 그대로 두고 브리프만 갱신한다. 기존 값이 다르거나 유효하지 않으면 두 파일 모두 쓰지 않고 실패한다. 기존 브리프도 보존한다. 우회용 강제 덮어쓰기 옵션은 제공하지 않는다.
- YAML은 단일 매핑 문서여야 한다. 중복 키와 잘못된 YAML은 오류다. 출력 경로의 심볼릭 링크는 따라가지 않는다.
- 브리프는 재생성되는 파일이다. 입력·설정 검증을 모두 마친 뒤 각 파일을 임시 파일로 작성하고 교체한다. 여러 파일의 교체를 하나의 트랜잭션으로 보장하지는 않는다.

생성 예시:

```yaml
# .deploy/config.yaml
compliance: regulated
```

## 검증

자동 테스트는 `tests/test_write_brief.py`에 있다. 새 앱에서 분류별 파일 생성, 명시적 건너뛰기, 잘못된 입력, 기존 설정·주석 보존, 규제 분류 변경 차단, dry-run을 확인한다.

Claude Code 대화 검증은 클라우드가 필요 없는 임시 앱 디렉터리에서 한다.

1. 스킬을 설치하고 `/deploy-analyze`를 실행한다. 질문이 다섯 항목을 다루고 답변을 기다리는지 확인한다.
2. `하루 100명 / 월 10만 원 / 회원 이메일 저장 / AWS / 시연용`으로 답한다. 브리프와 `compliance: regulated`가 생기는지 확인한다.
3. 별도 빈 디렉터리에서 데이터 종류를 모두 취급하지 않는다고 답한다. `none`이 생성되는지 확인한다.
4. 별도 빈 디렉터리에서 모름/건너뛰기로 답한다. `regulated`와 미정 근거가 남는지 확인한다. 질문을 취소한 경우 저장을 진행하지 않아야 한다.
5. 이미 `regulated`인 디렉터리에서 모두 해당 없다고 답한다. 스킬이 보호 오류를 안내하고 기존 두 파일을 보존하는지 확인한다.
