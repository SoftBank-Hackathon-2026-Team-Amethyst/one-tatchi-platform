# 서비스 분석기

이 웹앱이 서비스로서 무엇을 하고, 그 성격이 배포에 무엇을 요구하는지 알아낸다.

## 조사할 것

- **무엇을 하는가.** 주요 기능과 사용자. README · docs · 라우트 · 화면 · 데이터 모델에서 읽는다.
- **다루는 데이터.** 개인정보 · 결제 · 인증 정보 같은 민감 데이터가 있는지. 데이터 모델의 필드 이름과 입력 폼을 본다. 브리프의 민감 데이터 답변(`handles_sensitive_data`)과 비교한다. 코드에서 로그인 · 결제를 찾았는데 답변이 `no`면 그 사실을 결과에 적는다(답변을 고치지는 않는다. `compliance`는 사람이 정한다).
- **보관 위치 요구.** 서비스 성격(금융 · 결제 · 공공)상 데이터가 국내 또는 사내에 있어야 하는지. 배포 대상 추천 규칙 1번의 입력이다.
- **중단의 영향.** 멈추면 누가 어떻게 곤란한가. 내부 도구인지 고객용인지. 브리프의 가용성 답변(`availability`)과 맞춰 본다.
- **사용 패턴.** 읽기 위주인지 쓰기 위주인지, 실시간 연결 · 백그라운드 작업 · 예약 작업이 있는지.
- **외부 의존.** 호출하는 외부 API · 서비스. 배포 대상에서 닿아야 한다.

## 정할 것

- 가용성 수준: 인스턴스 하나로 충분한가, 이중화가 필요한가. 시연용(`demo`)은 `replicas: 1`로 둔다.
- 데이터 보관 위치 제한: 없음 / 데이터만 사내 / 전부 사내.
- 릴리스 때 주의할 것: 오래 가는 연결, 진행 중인 작업, 이전 버전과 호환되지 않는 스키마 변경(Blue-Green에서는 두 버전이 같은 DB를 쓴다).
- smoke 요청 후보: 승격 판단(T7)이 green에 보낼 읽기 요청 목록. 쓰기 요청은 데이터를 남기므로 꼭 필요한 것만, 그리고 테스트용임이 드러나는 값으로.
